## Getting started

This pattern works with any headless browser and any automation library that drives it.
The image is whatever your Dockerfile produces: Chromium driven by Puppeteer, Firefox driven by Playwright, or any other pairing.
This guide uses one such combination: [Puppeteer](https://pptr.dev/), a Node.js library which provides a high-level API to control browsers, including the option to run them headless (no UI).

To run it, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/node-express-puppeteer/` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/node-express-puppeteer/
   ```

Make sure to log into Unikraft Cloud and pick a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

:::caution
A Puppeteer instance on Unikraft Cloud requires 4GB to run.
Request an increase in the instance memory quota if you need more memory.
:::

When done, invoke the following command to deploy this app on Unikraft Cloud.
The `--scale-to-zero` flag enables stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero), so the browser suspends with its memory intact when idle and resumes on the next request:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/httpserver-node-express-puppeteer:latest
unikraft run --metro fra \
  -p 443:3000/tls+http \
  -m 4G \
  --scale-to-zero policy=idle,cooldown-time=1000,stateful=true \
  --image <my-org>/httpserver-node-express-puppeteer:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 4Gi \
  -p 443:3000/tls+http \
  --scale-to-zero idle \
  --scale-to-zero-cooldown 1s \
  --scale-to-zero-stateful \
  .
```

</CodeTabs>

## Running a browser per job

Scraping runs and test suites arrive in bursts, and a browser is busy for the length of one job.
Attach more instances to the service the deploy created and the external load balancer spreads jobs across them:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  -m 4G \
  --service little-snow-7qwu6vv5 \
  --scale-to-zero policy=idle,cooldown-time=1000,stateful=true \
  --image <my-org>/httpserver-node-express-puppeteer:latest
```

```bash title="kraft"
kraft cloud instance create \
  --start \
  -M 4Gi \
  --service little-snow-7qwu6vv5 \
  --scale-to-zero idle \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 1s \
  --image <my-org>/httpserver-node-express-puppeteer:latest
```

</CodeTabs>

The service name comes from the deploy output above.
Each browser keeps its own stateful scale-to-zero setting, so the extra instances sit suspended and cost nothing between bursts, and [load balancing](/features/load-balancing) wakes one when a job needs it.
Use `--replicas n` to start a group in one command, or turn on [autoscale](/features/autoscale) for the service to let the platform add and remove browsers as load moves.

## Customize your deployment

The current deployment uses an ExpressJS service that uses the [PDF generating functionality of Puppeteer](https://devdocs.io/puppeteer/).
Customizing the deployment means updating the service, such as adding new functionalities provided by Puppeteer.
You can update the service to provide a REST-like interface.

## Why this pattern works

Headless browsers power web scraping, automated testing, Search Engine Optimization (SEO) rendering, and synthetic monitoring.
These workloads are resource-intensive, security-sensitive, and bursty, and each of those pressures maps to a platform feature:

1. **Hardware isolation for untrusted content**:
   A browser executes whatever JavaScript the pages it visits ship.
   Each browser on Unikraft Cloud runs in its own microVM with its own kernel, so a compromised page stays behind hardware-enforced boundaries, and the minimal OS footprint keeps the attack surface small.

1. **Stateful suspend instead of cold Chromium starts**:
   Launching Chromium from scratch takes seconds.
   Stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) snapshots the whole microVM, browser process included, and resumes it in under 10 ms with its memory intact.

1. **Capacity that follows the burst**:
   Scraping runs, test suites, and monitoring checks arrive in short, irregular spikes.
   Instances boot in milliseconds and [autoscale](/features/autoscale) adds or removes browsers in milliseconds, so you pay for the seconds of actual execution rather than for a standing pool.

1. **A serverless building block**:
   Because a browser wakes on an incoming request, you can trigger it directly from APIs, webhooks, or [serverless functions](/use-cases/serverless-functions) with no orchestration layer.
   Deploying to more than one [metro](/platform/metros) puts browsers close to the data sources they scrape and the sites they watch.
