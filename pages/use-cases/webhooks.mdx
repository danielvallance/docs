Give every webhook source its own receiver: a hardware-isolated microVM that sleeps between deliveries and wakes in milliseconds when the next event arrives.

<ValueCards>
  <ValueCard title="Asleep until an event arrives" metric="wakes in milliseconds" metricHref="/features/scale-to-zero">
    Deliveries are sporadic, so a receiver spends most of its life waiting.
    [Scale-to-zero](/features/scale-to-zero) parks yours between events, and the delivery itself wakes it.
  </ValueCard>
  <ValueCard title="Bursts without a standing fleet" metric="scales out in milliseconds" metricHref="/features/autoscale">
    A merge storm or a batch of retried deliveries lands all at once.
    [Autoscale](/features/autoscale) brings receivers up as events arrive, and takes them away afterward.
  </ValueCard>
  <ValueCard title="A receiver per source, not one shared handler" metric="1 microVM per receiver">
    Each receiver is its own microVM with its own kernel and its own HTTPS endpoint.
    Payloads from GitHub, Stripe, or a partner integration stay behind hardware-enforced boundaries, and an idle receiver costs nothing.
  </ValueCard>
</ValueCards>

## Getting started

This pattern works with any webhook source, since the receiver is whatever your Dockerfile produces.
This guide deploys a GitHub webhook receiver that listens for repository events, written in Node.js with Express and the official [Octokit webhooks library](https://www.npmjs.com/package/@octokit/webhooks).
To run it, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/github-webhook-node/` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/github-webhook-node/
   ```

Make sure to log into Unikraft Cloud and set your token and a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

When done, build and deploy the receiver.
`GITHUB_WEBHOOK_SECRET` is the secret the receiver uses to verify incoming deliveries, so set it to a high-entropy string and give GitHub the same value later.
The `--scale-to-zero` flag enables stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero), so the receiver suspends one second after the last delivery and the next delivery wakes it:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/github-webhook-node:latest
unikraft run --metro fra \
  -m 1G \
  -p 443:3000/tls+http \
  --scale-to-zero policy=on,cooldown-time=1000,stateful=true \
  -e GITHUB_WEBHOOK_SECRET=your_secret_here \
  --image <my-org>/github-webhook-node:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 1Gi \
  -p 443:3000/tls+http \
  --scale-to-zero on \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 1s \
  -e GITHUB_WEBHOOK_SECRET=your_secret_here \
  .
```

</CodeTabs>

The `-p 443:3000/tls+http` mapping creates a [service](/platform/services), which is what makes the receiver reachable over HTTPS.
Most webhook senders deliver only to HTTPS endpoints, and this gives you one: the platform exposes the instance on a subdomain of `unikraft.app` and issues its [certificate](/platform/certificates) for you.
The output includes the FQDN to hand to GitHub.

Check that the receiver is up:

```bash
curl https://<your-server-fqdn>/health
```

```text title=""
{"status":"healthy","timestamp":"2025-12-17T14:55:20.953Z","uptime":0.063799807}
```

To create a webhook in GitHub, follow the [official documentation](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks) and the indications in the example's README.
Point it at `https://<your-server-fqdn>/webhook` and give it the same secret you deployed with.

The example includes:

* **Signature validation** using GitHub's webhook secret (via Octokit library).
* **Event logging** with timestamps for debugging and auditing.
* **Health check** endpoint for monitoring and load balancer integration.

## Absorbing delivery bursts

A retry storm or a batch of queued deliveries arrives all at once.
Attach a second receiver to the service the deploy created, and the external load balancer spreads deliveries across both:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  -m 1G \
  --service <service-name> \
  --scale-to-zero policy=on,cooldown-time=1000,stateful=true \
  -e GITHUB_WEBHOOK_SECRET=your_secret_here \
  --image <my-org>/github-webhook-node:latest
```

```bash title="kraft"
kraft cloud instance create \
  --start \
  -M 1Gi \
  --service <service-name> \
  --scale-to-zero on \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 1s \
  -e GITHUB_WEBHOOK_SECRET=your_secret_here \
  --image <my-org>/github-webhook-node:latest
```

</CodeTabs>

The service name comes from the deploy output above.
The second receiver waits on standby and costs nothing until [load balancing](/features/load-balancing) sends it a delivery.
To let the platform own the instance count instead, turn on [autoscale](/features/autoscale) for the service.

To customize for other webhook sources ([Stripe](https://docs.stripe.com/webhooks), [Slack](https://docs.slack.dev/tools/node-slack-sdk/webhook/), [GitLab](https://docs.gitlab.com/user/project/integrations/webhooks/), etc.), it's best to refer to their specific libraries and signature validation methods.
Webhooks aren't a standardized protocol, so each service has its own conventions.
Also follow [Webhooks.fyi](https://webhooks.fyi/) for best practices.

## Why this pattern works

A webhook endpoint has to answer a request that arrives without warning, from a system you don't control, on a schedule nobody sets:

1. **Wake-up that fits inside the sender's timeout**:
   [Scale-to-zero](/features/scale-to-zero) puts an idle receiver on standby, and the next delivery cold boots it again within milliseconds.
   Senders allow an endpoint only seconds to respond, then retry the delivery and eventually disable the hook, so the wake-up has to stay well under that budget.
   The [`idle` policy](/features/scale-to-zero#policies) also parks receivers holding open but inactive connections, and incoming packets wake them without dropping the connection.

1. **An HTTPS endpoint from the first deploy**:
   Attaching a [service](/platform/services) exposes the instance on a subdomain of `unikraft.app`, and the platform issues a certificate for it from a public certificate authority.
   The external load balancer terminates TLS before traffic reaches the receiver, which leaves signature validation as the only cryptography your code performs.
   When you would rather hand out an address on a domain you own, point it at the metro with a CNAME and attach your own [domain](/platform/domains).

1. **Isolation for payloads you didn't write**:
   A receiver parses data that arrives from outside your systems, sometimes before signature validation gets a chance to reject it.
   Each instance runs as its own microVM with its own kernel and hardware-level isolation, so one receiver reaches neither the memory nor the files of another.
   A receiver per source keeps a crash, a bad payload, or a compromise contained to the integration that caused it.

1. **Bursts absorbed by waking instances, not by provisioning them**:
   Attaching more than one instance to a service turns on [load balancing](/features/load-balancing), which counts in-flight requests for HTTP services and open connections for TCP ones.
   A per-instance soft limit tells the load balancer when to wake another standby instance, and a hard limit caps how many requests a single instance takes.
   [Autoscale](/features/autoscale) takes over the instance count entirely and scales out in milliseconds, which matches replays and retry storms that arrive with no notice.

1. **Density that makes a receiver per integration cheap**:
   A single server holds up to 100K+ microVMs, and Unikraft Cloud charges for active vCPU time, so a receiver nobody calls costs nothing.
   That turns one receiver per source, per tenant, or per [metro](/platform/metros) into a design decision rather than a budget one.
   Specialized receivers stay small, and you pay for the events you process rather than for the hours you wait.
