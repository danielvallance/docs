Give every world or match its own game server: a hardware-isolated microVM that cold-starts in under 10 ms and sleeps at zero cost between sessions.

<ValueCards>
  <ValueCard title="Cold start in milliseconds" metric="boots in < 10 ms" metricHref="/platform/instances#instance-templates">
    Expensive startup work, such as world initialization, happens once in a [template](/platform/instances#instance-templates) snapshot.
    Every server after that boots from the template.
  </ValueCard>
  <ValueCard title="Pause the world, keep the state" metric="resumes in < 10 ms" metricHref="/features/scale-to-zero#stateful-scale-to-zero">
    When the last player disconnects, [stateful scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) suspends the server with its memory intact.
    The next connection wakes it exactly where it left off.
  </ValueCard>
  <ValueCard title="Isolated VMs, superior unit economics" metric="100K+ microVMs / server" metricHref="/features/scale-to-zero">
    Each game server is a strongly isolated virtual machine, not a container.
    A single physical node hosts 100K+ microVMs, so a dedicated microVM per world stays affordable.
  </ValueCard>
</ValueCards>

## Getting started

This pattern works with any game server.
This guide uses Minecraft, whose expensive JVM startup and world initialization make the [template](/platform/instances#instance-templates) model shine.
A template is a preinitialized snapshot of an instance that new instances clone from, resuming its exact system state.
The [`minecraft`](https://github.com/unikraft-cloud/examples/tree/main/minecraft) example builds its base image from [itzg/minecraft-server](https://hub.docker.com/r/itzg/minecraft-server) (Java 25) and includes:

- A `wrapper.sh` entrypoint that starts SSH, loads configuration from a [ROM](/features/roms)—a read-only blob of code or data attached to an instance at creation—and disables [scale-to-zero](/features/scale-to-zero) during initialization.
- Patched startup scripts that snapshot the instance into a template before full server warm-up.

### Prerequisites

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

2. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/minecraft/` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/minecraft/
   ```

3. Review and adjust the base server settings in [`base/.env`](https://github.com/unikraft-cloud/examples/tree/main/minecraft/base/.env).
   You can check out [this documentation](https://docker-minecraft-server.readthedocs.io/en/latest/) for available configuration options.
   Make sure to also set your `PUBKEY` for SSH access, and optionally set `TEMPLATE_WITH_WORLD` if you want the template to include the world (see below).
   Optionally, create per-config overrides in `<config>/.env`.
   All `.env` files are packaged as [auxiliary ROMs](/features/roms) and mounted at `/rom/<config>`.

Make sure to log into Unikraft Cloud and pick a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
export UKC_METRO=fra
```

</CodeTabs>

### Step 1: Package and push the base image

First, package and push the base Minecraft server image:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/minecraft:latest
```

```bash title="kraft"
kraft pkg \
  --name index.unikraft.io/<my-org>/minecraft:latest \
  --plat kraftcloud \
  --arch x86_64 \
  --rootfs-type erofs \
  --push \
  .
```

</CodeTabs>

The image contains the files from the Docker image [itzg/minecraft-server](https://hub.docker.com/r/itzg/minecraft-server) and includes a few tweaks:

- The entrypoint uses a custom `wrapper.sh` script that:
  - Starts an SSH server
  - Loads the environment configuration from the attached [ROMs](/features/roms)
  - Disables [scale-to-zero](/features/scale-to-zero) before executing the original entrypoint
- The server configuration scripts from the original image have patches to trigger the [template](/platform/instances#instance-templates) snapshot, which allows faster instance creation from the template.
  Scale-to-zero is then re-enabled after server initialization.

### Step 2: Create a template from the base image

Boot a short-lived instance from the base image.
The startup script snapshots it into a [template](/platform/instances#instance-templates) before world generation, then the instance exits.

Pass your server settings as a [ROM](/features/roms):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  --name minecraft-tpl \
  -m 4096M \
  --vcpus 4 \
  --image <my-org>/minecraft:latest \
  --rom dir=base,at=/rom/base
```


You can configure the exact moment of snapshotting in [`patches/start-finalExec`](https://github.com/unikraft-cloud/examples/tree/main/minecraft/patches/start-finalExec) or with the following environment variable:

- If `TEMPLATE_WITH_WORLD=true`, then the snapshot will trigger **after** world generation
- Otherwise, the snapshot will trigger after extracting the jar files and writing configuration files, **before** world generation

### Step 3: Launch a server from the template

The `--scale-to-zero` flag (with `stateful=true`) enables [stateful scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero): when the last player disconnects, the server suspends with its memory intact and wakes on the next connection.

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  --name minecraft \
  -p 2222:2222/tls \
  -p 25565:25565/tls \
  --scale-to-zero policy=on,cooldown-time=5000,stateful=true \
  --template minecraft-tpl
```

## Connect to the server

:::caution[**Limited Access**]
At the moment, Unikraft Cloud exposes services over TLS.
Minecraft and SSH clients speak plain TCP, so use `socat` to end TLS locally.
:::

### Minecraft

```bash
socat TCP-LISTEN:25565,reuseaddr,fork OPENSSL:hidden-water-ewr8l9sp.fra.unikraft.app:25565,verify=0
```

Connect your Minecraft client to `localhost:25565`.

### SSH

```bash
socat TCP-LISTEN:2222,reuseaddr,fork OPENSSL:hidden-water-ewr8l9sp.fra.unikraft.app:2222,verify=0
```

Connect to `localhost:2222` with username `root` and the SSH key set in `.env`.

## Administration

### Remote console

SSH into the instance, then:

```bash
rcon-cli --host 127.0.0.1
```

Example commands:

```text title=""
say Hello from Unikraft Cloud!
/op <username>
```

### Whitelist in offline mode

Offline mode generates UUIDs that differ from online UUIDs.
Compute the correct UUID per username and add it to `/data/whitelist.json`:

```python
import hashlib, uuid; h = hashlib.md5(b'OfflinePlayer:<username>').digest(); u = uuid.UUID(bytes=h); print(u)
```

## Why this pattern works

1. **Warm starts from template snapshots**: game servers have expensive startup paths, such as loading assets, warming the JVM, and initializing the world.
   [Instance templates](/platform/instances#instance-templates) snapshot the server after that work completes, so every later start boots warm in milliseconds instead of repeating it.

1. **Stateful suspend fits session-based play**: when the last player disconnects, [stateful scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) suspends the microVM with its memory intact—world, entities, JVM heap.
   The next connection resumes the same process: no restart, no save/load cycle.

1. **Hardware isolation per server**: each game server runs in its own microVM with its own kernel.
   No shared kernel between tenants, no container-escape surface, and no noisy-neighbour risk when one world spikes.

1. **Density that changes the economics**: a single server hosts 100K+ microVMs, and an idle world costs nothing.
   A dedicated server per world, match, or community becomes affordable at fleet scale.

1. **Configuration as [ROMs](/features/roms), not rebuilds**: server settings ship as read-only images attached at instance creation.
   Distinct server variants come from swapping a ROM rather than rebuilding the base image.
