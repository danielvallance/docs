Give every task its own sandbox: a hardware-isolated microVM, booted from a snapshot in under 10 ms, gone when the work ends.

<ValueCards>
  <ValueCard title="Run untrusted code safely" metric="1 microVM per task">
    Every sandbox is a dedicated microVM with its own kernel.
    Code written by agents, user submissions, and third-party plugins stay behind hardware-enforced boundaries.
  </ValueCard>
  <ValueCard title="Start big environments instantly" metric="boots in < 10 ms" metricHref="/platform/instances#instance-templates">
    Pack GBs of tools and models into a [template](/platform/instances#instance-templates) and launch sandboxes from it in milliseconds.
    [Branch](/features/branching) a running sandbox to spawn sub-agents mid-task.

  <ValueCard title="Scale to swarms, pay for work" metric="up to 100K+ sandboxes / server">

## Getting started

This pattern works with whatever you need to sandbox: a language runtime executing user-submitted code, a data-processing job, a browser automation run, or a third-party plugin.
The image is whatever your Dockerfile produces, and every sandbox gets the same microVM boundary regardless of what runs inside.

{/* vale off */}

This guide uses one such workload: [OpenClaw](https://openclaw.ai/), an autonomous AI agent framework that runs in an isolated microVM on Unikraft Cloud.

{/* vale on */}

This guide explains how to create and deploy your own OpenClaw gateway on Unikraft Cloud.
To run this example, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/openclaw` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/openclaw/
   ```

Make sure to log into Unikraft Cloud and pick a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

The `UKC_TOKEN` and `UKC_METRO` environment variables are only supported by the legacy CLI.

When done, you may create the OpenClaw Unikraft Cloud image and deploy an instance from it like so.
The `--scale-to-zero` flag enables stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero), so the sandbox suspends with its memory intact when idle and resumes on the next connection:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/openclaw:latest
unikraft run --metro fra \
  -m 4G \
  -p 18789:18789/tls \
  -p 2222:2222/tls \
  --scale-to-zero policy=on,cooldown-time=10000,stateful=true \
  -e PUBKEY="...." \
  --image <my-org>/openclaw:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 4Gi \
  -p 18789:18789/tls \
  -p 2222:2222/tls \
  --scale-to-zero on \
  --scale-to-zero-cooldown 10s \
  --scale-to-zero-stateful \
  -e PUBKEY="..." \
  .
```

</CodeTabs>

Make sure to replace `<my-org>` with your username / org-name and to set your SSH public key as the `PUBKEY` environment variable above.

## OpenClaw Setup

{/* vale on */}

Once you have SSH'd into your instance, you may run:

```bash
openclaw onboard
```

This will set up your OpenClaw gateway on the instance.
You will have to provide your LLM's API key here.

Once done, make note of your `gateway.auth.token` (henceforth referenced as `<token>`) from `~/.openclaw/openclaw.json`

```bash
cat ~/.openclaw/openclaw.json
```

Set `gateway.controlUi.allowedOrigins` in `~/.openclaw/openclaw.json`:

```json title="openclaw.json"
...
  "gateway": {
    ...
    "controlUi": {
      "allowedOrigins": [
        "https://proud-smoke-cjf0wro8.fra.unikraft.app:18789"
      ]
    },
    ...
  },
...
```

Replace the address above with the address of your instance (noted earlier).

Run the gateway:

```bash
openclaw gateway run --bind lan
```

You may now access the web dashboard at the following address:

```text title=""
https://<address>:18789?token=<token>
```

Where `<address>` is your above noted address and `<token>` is your above noted token.

For security reasons, you will have to manually approve your web "device" to start using the web dashboard.
Create a new SSH connection to your OpenClaw instance:

```bash
ssh -l root localhost -p 2222
```

First, find your device ID:

```bash
openclaw devices list
```

Look under the `Request` column.
Device IDs look like `cabd915e-137a-4bc4-b640-d0e507684d65`

Finally, approve your device with:

```bash
openclaw devices approve <device-id>
```

Once you approve your device, refresh your OpenClaw web dashboard.

You now have full access to your own OpenClaw deployment on Unikraft Cloud!

## One sandbox per task

The deployment above gives you one long-lived sandbox.
To hand every task its own, snapshot the initialized sandbox into a [template](/platform/instances#instance-templates) and clone it per task.
Cloning restores the template's exact system state, so a sandbox packed with GBs of tools still starts in milliseconds.

Turn the running instance into a template:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft instance template create openclaw-8tosm
```

```bash title="kraft"
kraft cloud instance template create openclaw-8tosm
```

</CodeTabs>

Then start a sandbox per task from it.
The `--rm` flag deletes the instance when it stops, so a sandbox disappears with the task that needed it:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  --template openclaw-8tosm \
  --name sandbox-task-1 \
  -p 18789:18789/tls \
  -p 2222:2222/tls \
  --scale-to-zero policy=on,cooldown-time=10000,stateful=true \
  --rm
```

```bash title="kraft"
kraft cloud instance create \
  --start \
  --template openclaw-8tosm \
  --name sandbox-task-1 \
  -p 18789:18789/tls \
  -p 2222:2222/tls \
  --scale-to-zero on \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 10s \
  --feature delete-on-stop
```

</CodeTabs>

## Checkpointing a long-running sandbox

:::caution[**Limited Access**]
Checkpointing is a new feature that **is not** enabled by default and requires a valid license.
The interface described here reflects the current implementation and may change before general availability.
:::

An agent that has been working for an hour holds context you don't want to lose to a bad step.
[Checkpointing](/features/checkpoints) captures a running sandbox's complete state, memory and volume, without interrupting it.
Call the [`POST /instances/checkpoints`](/api/platform/v1/instances) endpoint with the source instance name:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances/checkpoints \
  -d '{
    "name": "before-risky-step",
    "from": {
      "name": "openclaw-8tosm"
    }
  }'
```

</CodeTabs>

Later, roll back by creating a fresh sandbox from that checkpoint:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances \
  -d '{
    "name": "openclaw-restored",
    "checkpoint": {
      "name": "before-risky-step"
    }
  }'
```

</CodeTabs>

A bad step then costs you a restore rather than the whole task.

## Branching a sandbox for sub-agents

:::caution[**Limited Access**]
Instance branching is a preview feature and isn't yet available on the public Unikraft Cloud.
The interface described here reflects the current implementation and may change before general availability.
:::

When a task needs to explore two or more approaches at once, [branch](/features/branching) the running sandbox instead of building each sub-agent's context from scratch.
Each branch is an independent copy that starts from the source's exact memory and volume state, and the source keeps running unaffected:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances \
  -d '{
    "name": "sub-agent-1",
    "branch_from": {
      "name": "openclaw-8tosm"
    }
  }'
```

</CodeTabs>

A branch inherits the source's image, resources, and environment, so you can't set those in the request.
Repeat the call with a different `name` for each sub-agent you want to run in parallel.

## Cleanup

Remove the sandboxes you started, along with any branches, and then the template they clone from:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft instances delete openclaw-8tosm sandbox-task-1 sub-agent-1
unikraft instances template delete openclaw-8tosm
```

```bash title="kraft"
kraft cloud instance remove openclaw-8tosm sandbox-task-1 sub-agent-1
kraft cloud instance template remove openclaw-8tosm
```

</CodeTabs>

## Why this pattern works

Sandboxes on Unikraft Cloud combine four properties that normally trade off against each other:

1. **Hardware isolation without shared state**:
   Every sandbox is its own microVM with its own kernel, so there is no shared kernel between tenants.
   Hardware-enforced boundaries remove the container-escape risk that comes with namespace-based isolation, and the minimal OS footprint keeps the attack surface small for every run.

1. **Container-like startup speed**:
   Instances cold-boot in milliseconds, and [templates](/platform/instances#instance-templates) extend that to arbitrarily large environments by snapshotting a fully initialized sandbox once and cloning it per task.
   Long-running sandboxes resume from stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) with their memory intact, so you never need pre-warmed pools or reserved capacity.

1. **A cost model that fits bursty work**:
   Some sandboxes finish in milliseconds, others run for hours.
   [Scale-to-zero](/features/scale-to-zero) releases the resources of idle sandboxes and wakes them on the next request, so you pay for execution time rather than for idle infrastructure between tasks.

1. **Branch and checkpoint mid-task**:
   [Branching](/features/branching) clones a running sandbox in milliseconds, so a long-running task can split into parallel copies that inherit its exact memory and volume state instead of rebuilding context from scratch.
   [Checkpoints](/features/checkpoints) save a long-running sandbox without interrupting it, so a bad step costs you a restore rather than the whole task.
