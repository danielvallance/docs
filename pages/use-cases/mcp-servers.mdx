Give every agent session its own [MCP (Model Context Protocol)](https://modelcontextprotocol.io/docs/getting-started/intro) server: a hardware-isolated microVM that wakes on the first tool call and costs nothing while the model thinks.

<ValueCards>
  <ValueCard title="Asleep between tool calls" metric="wakes in milliseconds" metricHref="/features/scale-to-zero">
    An agent spends most of a session reasoning rather than calling tools.
    [Scale-to-zero](/features/scale-to-zero) parks the MCP server between calls and it wakes in milliseconds on the next call, so the waiting costs you nothing.
  </ValueCard>
  <ValueCard title="An isolated MCP server per session, not one shared endpoint" metric="1 microVM per session">
    MCP servers reach into file systems, databases, and internal APIs on a model's behalf, holding the credentials for each.
    Every server runs in its own microVM with its own kernel, so one session's tools stay out of another's reach.
  </ValueCard>
  <ValueCard title="Bring the server as it is" metric="starts in < 10 ms" metricHref="/platform/instances#instance-templates">
    Most MCP servers are Python or Node packages with heavy dependency trees, and the image is whatever your Dockerfile produces.
    Snapshot one as a [template](/platform/instances#instance-templates) once it has imported everything, and every server you start from it skips that work.
  </ValueCard>
</ValueCards>

## Getting started

This pattern works with any MCP server, since the image is whatever your Dockerfile produces.
This guide walks through two of them: a community server that fronts an external archive, and a minimal custom server you write yourself.

### Example 1: ArXiv MCP server

The [arXiv MCP Server](https://github.com/blazickjp/arxiv-mcp-server) is a community-made MCP server that connects AI tools directly to the [arXiv](https://arxiv.org/) archive of scientific articles and publications.
It allows MCP clients to browse and analyze papers.

To run an example based on it, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/mcp-server-arxiv/` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/mcp-server-arxiv/
   ```

Make sure to log into Unikraft Cloud and set your token and a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

When done, build and deploy the server.
The `--scale-to-zero` flag enables stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero), so the server suspends with its memory intact one second after the last tool call and resumes on the next one:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/mcp-server-arxiv:latest
unikraft run --metro fra \
  -m 2G \
  -p 443:8080/tls+http \
  --scale-to-zero policy=on,cooldown-time=1000,stateful=true \
  --image <my-org>/mcp-server-arxiv:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 2Gi \
  -p 443:8080/tls+http \
  --scale-to-zero on \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 1s \
  .
```

</CodeTabs>

## Building your own MCP server

MCP servers follow a simple pattern:

1. **Define tools**: Specify what capabilities your server provides (functions, APIs, data sources).
1. **Handle requests**: Process MCP protocol requests from AI assistants.
1. **Return results**: Format responses in the MCP protocol format.

Common use cases for custom MCP servers:

* **Database access**: Query internal databases, data warehouses, or analytics platforms.
* **API integration**: Connect AI assistants to third-party services (customer relationship management, ticketing, monitoring).
* **Custom business logic**: Integrate company-specific calculations, validations, or workflows.
* **Document retrieval**: Search and retrieve from internal knowledge bases or document stores.

Each of these fits in its own microVM rather than one endpoint exposing every tool.

## A server per agent session

The deployments above give you one long-lived server.
To hand each agent session its own, snapshot the running server into a [template](/platform/instances#instance-templates) once it has imported its dependencies, then clone the template per session.

Turn the instance you deployed above into a template:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft instance template create mcp-server-arxiv-l7l24
```

```bash title="kraft"
kraft cloud instance template create mcp-server-arxiv-l7l24
```

</CodeTabs>

Every clone then starts from that snapshot, with imports done and caches warm, instead of repeating startup.
Add `--rm` so the platform deletes the instance when it stops, which keeps per-session servers from piling up:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  --template mcp-server-arxiv-l7l24 \
  --name mcp-session-agent-42 \
  -p 443:8080/tls+http \
  --scale-to-zero policy=on,cooldown-time=1000,stateful=true \
  --rm
```

```bash title="kraft"
kraft cloud instance create \
  --start \
  --template mcp-server-arxiv-l7l24 \
  --name mcp-session-agent-42 \
  -p 443:8080/tls+http \
  --scale-to-zero on \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 1s \
  --feature delete-on-stop
```

</CodeTabs>

Repeat that command per session, changing `--name`, and each agent gets a server that shares no kernel with any other.
For cleanup rules that outlive a single instance, such as deleting a server a set time after it stops or after it has served a set number of requests, use [autokill](/features/autokill) instead of `--rm`.
Instances cloned from a template inherit the template's autokill configuration.

## Cleanup

Remove the servers you started, along with any per-session clones, and then the template:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft instances delete mcp-server-arxiv-l7l24 mcp-session-agent-42
unikraft instances template delete mcp-server-arxiv-l7l24
```

```bash title="kraft"
kraft cloud instance remove mcp-server-arxiv-l7l24 mcp-session-agent-42
kraft cloud instance template remove mcp-server-arxiv-l7l24
```

</CodeTabs>

## Why this pattern works

An MCP server sits inside an agent's loop: called in bursts, trusted with real credentials, and abandoned the moment the session ends:

1. **Wake-up that disappears into the model's own latency**:
   [Scale-to-zero](/features/scale-to-zero) puts an idle server on standby, and the next tool call cold boots it again within milliseconds.
   The model already spends far longer generating that call than the instance spends starting, so the wake-up never reaches the user.
   Servers with heavy startup work, such as a Python server importing a large dependency tree, pay that cost once.
   Snapshot the initialized server as an [instance template](/platform/instances#instance-templates), and every clone resumes from that state, memory and warm caches included, in under 10 ms.
   A long-lived server gets the same effect from [stateful scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero), which snapshots the instance before standby and loads that memory back on the next request.

1. **Isolation for tools that hold real credentials**:
   A server reaches file systems, databases, and third-party APIs on the model's behalf, with tokens for each of them.
   Each instance runs as its own microVM with its own kernel and hardware-level isolation, so a tool call steered by a poisoned document stays inside the microVM that ran it.
   The image carries only what that server needs, which keeps the attack surface small.

1. **Cleanup you configure once**:
   Servers created per session pile up unless something removes them.
   [Autokill](/features/autokill) deletes an instance a set time after it stops, or once it has served a set number of requests, and it can remove a [service group](/platform/services) after its last instance leaves.
   Instances cloned from an [instance template](/platform/instances#instance-templates) inherit that configuration, so the rule follows every server you start from it.

1. **Density that makes a server per integration affordable**:
   A single physical node holds up to 100K+ microVMs, and Unikraft Cloud charges for active vCPU time, so a server nobody calls costs nothing.
   That turns a specialized server per integration, per team, or per tenant into a design decision rather than a budget one, and keeps each one small enough to reason about.

1. **A server in the metro your agent talks to**:
   Every tool call inserts a network round trip into the model's loop, so distance shows up in the answer.
   Deploying the same image to more than one [metro](/platform/metros) puts the server near its clients, and idle regional servers wait at zero cost.
