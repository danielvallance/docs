Give every developer or branch a full development environment in the browser: a microVM that scales to zero shortly after the developer disconnects and restores, terminals and all, in under 10 ms.

<ValueCards>
  <ValueCard title="Pick up exactly where you left off" metric="restores in < 10 ms" metricHref="/features/scale-to-zero#stateful-scale-to-zero">
    An idle environment [scales to zero](/features/scale-to-zero#stateful-scale-to-zero), so nobody pays for the hours a developer is away.
    It restores in under 10 ms, with editors, terminals, and language servers exactly where they were.
  </ValueCard>
  <ValueCard title="A workspace that outlives the instance" metric="files on a volume" metricHref="/platform/volumes">
    Repositories, dependencies, and build caches live on a [volume](/platform/volumes) (persistent storage you attach to an instance).
    Rebuild the image or delete the instance, and the next one mounts the same files.
  </ValueCard>
  <ValueCard title="An isolated environment per developer or branch" metric="1 microVM per workspace">
    Dependency install scripts, test suites, and coding agents all run inside a microVM with its own kernel.
    Nothing they do reaches another developer, and an idle environment costs nothing.
  </ValueCard>
</ValueCards>

## Getting started

This pattern works with any browser-based IDE, since the image is whatever your Dockerfile produces.
This guide uses [Code Server](https://code.visualstudio.com/docs/remote/vscode-server), which runs [Visual Studio Code](https://code.visualstudio.com/) on a remote machine and serves it to a browser or a local VS Code client.
The deployment below mounts a volume at `/workspace` and turns on stateful [scale-to-zero](/features/scale-to-zero), so the environment scales to zero four seconds after the last connection and restores on the next one.

To run it, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/visual-studio-code-server/` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/visual-studio-code-server/
   ```

Make sure to log into Unikraft Cloud and pick a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪).

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

The `UKC_TOKEN` and `UKC_METRO` environment variables are only supported by the legacy CLI.

When done, invoke the following command to deploy this app on Unikraft Cloud:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft volumes create --metro fra \
  --name code-workspace \
  --size 1G
unikraft build . --output <my-org>/visual-studio-code-server:latest
unikraft run --metro fra \
  -m 2G \
  -p 443:8443/tls+http \
  --volume code-workspace:/workspace \
  --scale-to-zero policy=on,cooldown-time=4000,stateful=true \
  -e PGUID=0 \
  -e PGID=0 \
  -e PASSWORD=unikraft \
  -e SUDO_PASSWORD=unikraft \
  -e DEFAULT_WORKSPACE="/workspace" \
  --image <my-org>/visual-studio-code-server:latest
```

```bash title="kraft"
kraft cloud volume create \
  --name code-workspace \
  --size 1Gi
kraft cloud deploy \
  -M 2Gi \
  -p 443:8443 \
  --scale-to-zero on \
  --scale-to-zero-stateful \
  --scale-to-zero-cooldown 4s \
  -v code-workspace:/workspace \
  -e PGUID=0 \
  -e PGID=0 \
  -e PASSWORD=unikraft \
  -e SUDO_PASSWORD=unikraft \
  -e DEFAULT_WORKSPACE="/workspace" \
  .
```

</CodeTabs>

## Checkpointing an environment

:::caution[**Limited Access**]
Checkpointing is a new feature that **is not** enabled by default and requires a valid license.
The interface described here reflects the current implementation and may change before general availability.
:::

A volume keeps the files, but it doesn't capture the running environment.
[Checkpointing](/features/checkpoints) captures both, memory and volume together, without interrupting the session, which gives you a known-good environment to hand out or roll back to.
Call the [`POST /instances/checkpoints`](/api/platform/v1/instances) endpoint with the instance name:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances/checkpoints \
  -d '{
    "name": "course-week-1",
    "from": {
      "name": "code-server-6gxsp"
    }
  }'
```

</CodeTabs>

Then create environments from that checkpoint, each one starting from the same configured workspace:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances \
  -d '{
    "name": "code-server-student-1",
    "checkpoint": {
      "name": "course-week-1"
    }
  }'
```

</CodeTabs>

## Why this pattern works

A development environment is expensive to build, idle most of the day, and full of state a developer expects to survive lunch:

1. **Sessions that transparently scale-to-zero**:
   Once the cooldown expires, four seconds in the deployment above, stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) snapshots the instance's memory and scales it to zero.
   Nothing runs while the developer is away, so you pay nothing.
   The next connection starts the instance again and loads that snapshot, so the editor, its terminals, and its language servers come back exactly as they were, in under 10 ms.
   Without the stateful flag the instance boots from scratch instead, and the developer returns to an empty terminal.

1. **A workspace the instance doesn't own**:
   The environment mounts a [volume](/platform/volumes) at `/workspace`, so repositories, dependencies, and build caches live outside the instance.
   Delete the instance or rebuild the image, and the next instance mounts the same volume with the files intact.
   [Checkpoints](/features/checkpoints) (saved snapshots of a running instance) go further and capture memory and volume together, giving you an environment to restore from later.

1. **Isolation for code that runs all day**:
   A development environment executes untrusted code constantly: dependency install scripts, test suites, and coding agents.
   Each environment runs as its own microVM with its own kernel and hardware-level isolation, so none of that reaches another developer's environment.
   Builds and test runs behave the way they do locally.

1. **The rest of your stack, reachable but not exposed**:
   Every instance gets a private FQDN of the form `<instance-name>.internal` on your [private network](/platform/networking).
   The IDE reaches a database, a queue, or an internal API over that network, and none of them take traffic from the Internet.
   Only the published service, the IDE itself on port 443, has a public address.

1. **Density that makes an environment per branch affordable**:
   A single server holds up to 100K+ microVMs, and Unikraft Cloud charges for active vCPU time, so an environment nobody is using costs nothing.
   That covers a classroom of students, an environment per feature branch, or a distributed team whose machines idle overnight.
