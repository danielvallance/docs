Give every app or tenant its own database: a strongly isolated microVM that wakes on the first query, and clones itself in milliseconds.

<ValueCards>
  <ValueCard title="Run any database, isolated" metric="Postgres, MongoDB, Redis, ...">
    The image is whatever your Dockerfile produces: any database engine, any extensions.
    Each one runs as a hardware-isolated microVM with its own kernel, not a container.
  </ValueCard>
  <ValueCard title="Idle for free, wake instantly" metric="resumes in < 10 ms" metricHref="/features/scale-to-zero#stateful-scale-to-zero">
    Databases cold start in under 10 ms.
    Stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) suspends an idle database with its memory intact and resumes it on the next query.
  </ValueCard>
  <ValueCard title="Clone and restore in milliseconds" metric="branches in < 10 ms" metricHref="/features/branching">
    [Branch](/features/branching) a running database into an independent, byte-for-byte copy.

## Getting started

This pattern works with any database engine.
This guide shows you how to use [PostgreSQL](https://www.postgresql.org/), a powerful, open source object-relational database system, in a serverless fashion.
The instance will [scale-to-zero](/features/scale-to-zero) when not in use.

To run it, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/postgres/` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/postgres/
   ```

Make sure to log into Unikraft Cloud by setting your token and a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

The `UKC_TOKEN` and `UKC_METRO` environment variables are only supported by the legacy CLI.

When done, invoke the following command to deploy this app on Unikraft Cloud.
The `--scale-to-zero` flag enables stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero), so the database suspends with its memory intact when idle and resumes on the next query:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/postgres:latest
unikraft run --metro fra \
  -m 1G \
  -p 5432:5432/tls \
  --scale-to-zero policy=idle,cooldown-time=1000,stateful=true \
  -e POSTGRES_PASSWORD=unikraft \
  --image <my-org>/postgres:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 1Gi \
  -p 5432:5432/tls \
  --scale-to-zero idle \
  --scale-to-zero-cooldown 1s \
  --scale-to-zero-stateful \
  -e POSTGRES_PASSWORD=unikraft \
  .
```

</CodeTabs>

:::tip
This example uses the [`idle` scale-to-zero policy](/features/scale-to-zero) by default.
This means that the instance will use scale-to-zero even in the presence of `psql` connections.

The PostgreSQL example makes use of scale-to-zero app support.
This ensures that the instance isn't put into standby even for long running queries (during which the connections are also idle).
To this end, the example loads the [`pg_ukc_scaletozero`](https://github.com/unikraft-cloud/pg_ukc_scaletozero) module into PostgreSQL.
This module suspends scale-to-zero during query processing.
You can see this in action by running `SELECT pg_sleep(10);` and verifying that the instance keeps on running.
:::

## Using volumes

You can use [volumes](/platform/volumes) for data persistence for your PostgreSQL instance.

For that you would first create a volume:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft volumes create --metro fra \
  --name postgres \
  --size 200M
```

```bash title="kraft"
kraft cloud volume create \
  --name postgres \
  --size 200Mi
```

</CodeTabs>

Then start the PostgreSQL instance and mount that volume:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/postgres:latest
unikraft run --metro fra \
  -m 1G \
  -p 5432:5432/tls \
  --scale-to-zero policy=idle,cooldown-time=1000,stateful=true \
  -e POSTGRES_PASSWORD=unikraft \
  -e PGDATA=/volume/postgres \
  --volume postgres:/volume \
  --image <my-org>/postgres:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 1Gi \
  -p 5432:5432/tls \
  --scale-to-zero idle \
  --scale-to-zero-cooldown 1s \
  --scale-to-zero-stateful \
  -e POSTGRES_PASSWORD=unikraft \
  -e PGDATA=/volume/postgres \
  -v postgres:/volume \
  .
```

</CodeTabs>

## Using checkpoints

:::caution[**Limited Access**]
Checkpointing is a new feature that **is not** enabled by default and requires a valid license.
The interface described here reflects the current implementation and may change before general availability.
:::

You can checkpoint a running PostgreSQL instance to capture its complete state—memory and volume—without interrupting it.
Checkpoints are reusable, named restore points that keep a history.
Start a fresh instance from any checkpoint to recover from a failed migration or an erroneous write.
For a full description of how checkpointing works, see the [checkpointing feature page](/features/checkpoints).

To checkpoint a running instance, call the [`POST /instances/checkpoints`](/api/platform/v1/instances) endpoint with the source instance name:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances/checkpoints \
  -d '{
    "name": "before-migration",
    "from": {
      "name": "<source-instance>"
    }
  }'
```

</CodeTabs>

Later, restore the database by creating a new instance from the checkpoint:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft api /v1/instances \
  -d '{
    "name": "restored-postgres",
    "checkpoint": {
      "name": "before-migration"
    }
  }'
```

</CodeTabs>

The new instance resumes from exactly the checkpointed state, while the source instance keeps running unaffected.

## Using instance branching

:::caution[**Limited Access**]
Instance branching is a preview feature and isn't yet available on the public Unikraft Cloud.
The interface described here reflects the current implementation and may change before general availability.
:::

You can branch a running PostgreSQL instance to create an independent copy with the exact same state.
The source instance keeps running unaffected.
For a full description of how branching works, see the [branching feature page](/features/branching).

To create a branch, pass `--branch` with the source instance name to `unikraft run`:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  -p 5432:5432/tls \
  --branch <source-instance>
```

```bash title="kraft"
# branching will not be supported in the legacy CLI
# use the unikraft CLI
```

</CodeTabs>

The branch boots immediately from the same state as the source.
Connect to it like any other instance.
Whatever you do, the source instance remains unaffected.

When you're done, remove the branch:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft instances delete <branch-name>
```

```bash title="kraft"
kraft cloud instance remove <branch-name>
```

</CodeTabs>

## Customize your deployment

Your deployment is a standard PostgreSQL installation.
Customizing the deployment means providing a different environment.

An obvious one is to use a different database password when starting PostgreSQL.
For that you use a different `POSTGRES_PASSWORD` environment variable when starting the PostgreSQL instance.

You could also use a different location to mount your volume or set more configuration options.

And, you can use the PostgreSQL instance in conjunction with a frontend service, [see the guide here](/platform/services).

## Why this pattern works

Databases are resource-hungry, slow to scale, and costly to operate at low utilisation, and each of those pressures maps to a platform feature:

1. **Isolation by design**:
Each database runs as its own microVM with its own kernel, so tenants never share a kernel the way containers do.
The minimal OS footprint keeps the attack surface small, which matters when every instance holds customer data.

1. **Scale-to-zero without cold-start penalties**:
Stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) suspends the whole microVM, buffer pools and caches included, and resumes it in under 10 ms on the next query.
Idle databases consume no resources, so a fleet can grow to thousands of instances while you pay only for active queries: a fit for spiky workloads, dev/test environments, and SaaS platforms with a database per tenant.
Because a database wakes on the first query, it composes with [serverless functions](/use-cases/serverless-functions) and [API gateways](/use-cases/api-gateways) into a back end with no always-on tier.

1. **Checkpoints for point-in-time recovery**:
[Checkpointing](/features/checkpoints) saves the complete state of a running microVM without interrupting execution.
Checkpoints are incremental and keep a history, so you can restore the database to any previous point to recover from a failed migration or an erroneous write.

1. **Branching for instant clones**:
[Branching](/features/branching) creates an identical, independent copy of a running database in milliseconds while leaving the original untouched.
Test migrations or destructive changes on a byte-for-byte copy of production before applying them.
