## Getting started

This pattern works with any language runtime.
This guide uses the [`node-code-execution`](https://github.com/unikraft-cloud/examples/tree/main/node-code-execution) example.
It deploys a Node.js runtime as the base image, then attaches JavaScript or TypeScript function [ROMs](/features/roms) (small, read-only data blobs) to instances of that runtime.

### Prerequisites

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

1. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/node-code-execution` directory:

   ```bash
   git clone https://github.com/unikraft-cloud/examples
   cd examples/node-code-execution/
   ```

Make sure to log into Unikraft Cloud and pick a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"

# Set metro to Frankfurt, DE

```

### Step 1: Package and push the base runtime image

The base image contains a Node.js server (`server.ts`) that loads a function from the attached ROM and executes it on each HTTP request.
Right before starting the server, it writes `1` to `/uk/libukp/template_instance`, which triggers Unikraft Cloud to convert the running instance into a [template](/platform/instances#instance-templates) (a pre-initialized snapshot).

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build . --output <my-org>/node-code-exec:latest
```

```bash title="kraft"
kraft pkg \
  --name index.unikraft.io/<my-org>/node-code-exec:latest \
  --plat kraftcloud \
  --arch x86_64 \
  --rootfs-type erofs \
  --push \
  .
```

</CodeTabs>

### Step 4: Create instances from the template with ROMs attached

Stamp out instances from the template, each with a different ROM.
New instances skip the cold-start initialization phase because they restore from the template snapshot.
The `--scale-to-zero` flag enables [scale-to-zero](/features/scale-to-zero), so each function releases its resources when idle and wakes on the next request.

Create the first instance with the JavaScript ROM attached:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft run --metro fra \
  --name node-exec-rom1 \
  -p 443:8080/tls+http \
  --scale-to-zero policy=on,cooldown-time=1000,stateful=true \
  --rom image=<my-org>/node-rom1:latest,at=/rom \
  --template node-exec
```

```bash title="API"
curl -X POST "https://api.fra.unikraft.cloud/v1/instances" \
  -H "Accept: application/json" \
  -H "Authorization: Bearer ${UKC_TOKEN}" \
  -H "Content-Type: application/json" \
```

## How it works

The ROM deployment model has three layers:

1. **Base runtime image**: A generic Node.js server that loads and executes code from a well-known path (`/rom/rom.js` or `/rom/rom.ts`).
   Push it once; it changes infrequently.

1. **Function [ROM](/features/roms)**: A read-only filesystem image containing only the function source file.
   Lightweight, fast to build and push.
   Attached to an instance at creation time and mounted in the guest's filesystem.
   Update a function by pushing a new ROM, and roll back by pointing at a previous version—the runtime image doesn't change.

1. **Instance [template](/platform/instances#instance-templates)**: A pre-initialized snapshot of the runtime, created automatically when the base image boots without a ROM.
   New instances boot from this snapshot, skipping initialization and reducing cold-start latency to milliseconds.

## Why this pattern works

Three numbers decide whether a function platform works: how long a request waits for a cold instance, what an idle function costs, and how much of your code a tenant boundary protects:

1. **Runtime initialization stays off the request path**:
   An [instance template](/platform/instances#instance-templates) holds the runtime with its interpreter loaded and its dependencies imported.
   Every instance cloned from it starts from that snapshot instead of initializing again, so adding a function is a clone that lands in milliseconds.
   Requests to a function that already exists take the other path.
   A function instance isn't discarded once it has answered: it parks in the [`standby` state](/platform/instances#instance-states), and the platform starts it again when the next request arrives.
   Setting `stateful=true`, as the deployment above does, snapshots that instance's memory before it parks and loads the snapshot back when a request wakes it, so repeat requests skip initialization as well.

1. **Deployments that move a payload, not an image**:
   A [ROM](/features/roms) carries the function source alone, so a deployment pushes kilobytes rather than rebuilding and pushing a runtime image.
   Rolling back means pointing an instance at a previous ROM, and the runtime image, the slow part that seldom changes, stays untouched.
   One base image can then back many specialized functions that share a single template.

1. **A tenant boundary per function, not per cluster**:
   Every function instance is its own microVM with its own kernel, so there is no shared kernel, no noisy-neighbor risk, and no container-escape surface between tenants.
   Functions typically run code that arrives from somewhere else, whether from a customer, a partner, or a model, and hardware isolation is what keeps one of those runs away from the next.
   The image carries only the runtime the function needs, which keeps the attack surface small.

1. **Economics that fit bursty traffic**:
   [Scale-to-zero](/features/scale-to-zero) means an idle function costs nothing, and a single server holds up to 100K+ microVMs, so even a large fleet of low-traffic functions stays cheap.
   Because Unikraft Cloud charges for active vCPU time, splitting one endpoint into a function per route, per tenant, or per [metro](/platform/metros) is a design decision rather than a budget one.
