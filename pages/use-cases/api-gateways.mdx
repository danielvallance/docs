Front your APIs with a gateway that costs nothing between bursts: a hardware-isolated microVM that wakes on the first request and keeps every back end off the public Internet.

<ValueCards>
  <ValueCard title="An edge that sleeps between requests" metric="wakes on the first request" metricHref="/features/scale-to-zero">
    Your gateway parks itself when traffic stops and cold boots again in milliseconds when it returns.
    [Scale-to-zero](/features/scale-to-zero) removes the always-on cluster you would otherwise pay for overnight.
  </ValueCard>
  <ValueCard title="Absorb peaks without a warm pool" metric="scales out in milliseconds" metricHref="/features/autoscale">
    API traffic spikes at launches and quiets down at night.
    [Autoscale](/features/autoscale) grows your edge with the traffic instead of ahead of it.
  </ValueCard>
  <ValueCard title="One public door to your services" metric="back ends stay private" metricHref="/platform/networking">
    Only the gateway needs a public address.
    [Private networking](/platform/networking) keeps functions, databases, and caches reachable from the gateway alone, and wakes them the same way.
  </ValueCard>
</ValueCards>

## Getting started

This pattern works with any API gateway or reverse proxy, since the image is whatever your Dockerfile produces.
This guide uses [Tyk](https://tyk.io/), a universal API management tool for Representational State Transfer (REST), GraphQL, gRPC and async APIs.
Tyk keeps API tokens and OAuth clients in Redis, so the deployment below pairs the gateway with a Redis instance that only the gateway can reach.

To run it, follow these steps:

1. Install the CLI.
   Use the [unikraft CLI](/docs/cli/unikraft) or the legacy [kraft CLI](https://unikraft.org/docs/cli/install).
   You need a [BuildKit](https://github.com/moby/buildkit) builder. The easiest way to get one is via [Docker](https://docs.docker.com/engine/install/).
   You can also set up and use BuildKit directly; see the [quick start](https://github.com/moby/buildkit#quick-start).

   :::note
   The unikraft CLI is the current standard, while kraft is the legacy version.
   Choose one of the CLIs below and only run the commands associated with it for the rest of this guide.
   :::

2. Clone the [`examples` repository](https://github.com/unikraft-cloud/examples) and `cd` into the `examples/tyk/` directory:

   ```bash title=""
   git clone https://github.com/unikraft-cloud/examples
   cd examples/tyk/
   ```

Make sure to log into Unikraft Cloud and pick a [metro](/platform/metros) close to you.
This guide uses `fra` (Frankfurt, 🇩🇪):

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft login
```

```bash title="kraft"
# Set Unikraft Cloud access token
export UKC_TOKEN=token
# Set metro to Frankfurt, DE
export UKC_METRO=fra
```

</CodeTabs>

## Redis

The `REDIS_PASSWORD` environment variable sets the Redis `requirepass` directive, and defaults to `unikraft`.
Build and deploy the Redis instance that backs Tyk.
The `--domain tyk-redis.internal` flag gives it a private FQDN on your [internal network](/platform/networking), so the gateway can reach it while the Internet can't.
Stateful [scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) suspends it with its memory intact, which keeps the cache warm across idle periods:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build ./redis --output <my-org>/redis:latest
unikraft run --metro fra \
  -m 256M \
  --scale-to-zero policy=idle,cooldown-time=1000,stateful=true \
  --domain tyk-redis.internal \
  -e REDIS_PASSWORD=unikraft \
  --image <my-org>/redis:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 256Mi \
  --scale-to-zero idle \
  --scale-to-zero-cooldown 1s \
  --scale-to-zero-stateful \
  --domain tyk-redis.internal \
  -e REDIS_PASSWORD=unikraft \
  ./redis/
```

</CodeTabs>

## Tyk

Build and deploy the Tyk instance.
The `-p 443:8080/tls+http` mapping creates a [service](/platform/services), the public entry point that terminates TLS and load balances across the instances behind it.
Here it forwards HTTPS traffic on port 443 to Tyk on port 8080:

<CodeTabs syncKey="cli">

```bash title="unikraft"
unikraft build ./tyk --output <my-org>/tyk:latest
unikraft run --metro fra \
  -m 256M \
  -p 443:8080/tls+http \
  --scale-to-zero policy=on,cooldown-time=1000 \
  --image <my-org>/tyk:latest
```

```bash title="kraft"
kraft cloud deploy \
  -M 256Mi \
  -p 443:8080/tls+http \
  --scale-to-zero on \
  --scale-to-zero-cooldown 1s \
  ./tyk/
```

</CodeTabs>

## Why this pattern works

A gateway sits on the request path of everything you serve, so its idle cost, its behavior under bursts, and its exposure all matter:

1. **No always-on tier**:
[Scale-to-zero](/features/scale-to-zero) puts an idle gateway on standby, and the platform cold boots it again on the next request within milliseconds, a negligible amount of time next to Internet round trips.
Gateways that take longer to initialize, such as Tyk reconnecting to Redis or a JVM-based proxy warming up, can use [stateful scale-to-zero](/features/scale-to-zero#stateful-scale-to-zero) instead, which suspends the microVM with its memory intact and resumes it in under 10 ms.
Internal traffic wakes instances the same way public traffic does, so the back ends behind the gateway sleep between calls too, and the whole request path idles at zero cost.

1. **Small enough to sit on the hot path**:
Every call to your APIs passes through the gateway, so any overhead the platform adds shows up in every response.
Instances cold boot in milliseconds and run in a small memory footprint.
That keeps the platform's share of each request small, and lets a single gateway instance serve more concurrent requests before you need a second one.
The external load balancer terminates TLS before traffic reaches the gateway, which keeps certificate work off it entirely.

1. **Bursts absorbed by waking instances, not by provisioning them**:
Attaching more than one instance to a [service](/platform/services) turns on [load balancing](/features/load-balancing) across them, which counts in-flight requests for HTTP services and open connections for TCP ones.
A per-instance soft limit tells the load balancer when to wake another standby instance, and a hard limit caps how many requests a single instance takes.
[Autoscale](/features/autoscale) takes over the instance count entirely and scales out in milliseconds, which removes the reason to keep hot spares around for peaks.

1. **A gateway in every metro, not one central cluster**:
A single server holds 100K+ microVMs, and Unikraft Cloud charges for active vCPU time, so a gateway nobody calls costs nothing.
That turns a gateway per environment, per tenant, or per [metro](/platform/metros) into a routing decision rather than a capacity one.
Regional gateways wait at zero cost until traffic reaches their region, which puts TLS termination and policy enforcement close to your users.

1. **Hardware isolation where the exposure is highest**:
The gateway faces the open Internet, which makes it the most attacked component of the stack.
Each instance runs as its own microVM with its own kernel and hardware-level isolation, so a compromised gateway shares no kernel with the rest of your deployment.
The image contains only what the gateway needs, which keeps the attack surface small, and deploying [by image digest](/platform/images) gives you the identical, immutable image on every start.

1. **Back ends the Internet can't route to**:
Only instances you attach to a public service take traffic from the Internet, and that traffic always travels through the external load balancer.
Instance-to-instance traffic instead uses each instance's private FQDN (`<instance-name>.internal`) and stays on your [private network](/platform/networking).
In this guide, Tyk holds the only public service, while Redis answers only at `tyk-redis.internal`.
The same split applies to [serverless functions](/use-cases/serverless-functions) and [databases](/use-cases/serverless-databases) behind the gateway.
